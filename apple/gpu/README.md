# Verilator на GPU Apple Silicon: пакетная симуляция

Цель — регрессия из многих прогонов одной модели (например, тысячи сидов) на GPU M4: по одному
экземпляру модели на GPU-поток, как в RTLflow (ICPP'22). Документ — рабочий, обновляется по ходу
прототипа.

## Roofline GPU M4 (`probe/roofline.mm`)

| Что | M4 (10 ядер GPU) |
|---|---|
| Копирование памяти | 99 ГБ/с (чтение + запись) |
| Целочисленные операции (xor/shift/add, 8 независимых цепочек) | 1.5 Топ/с |
| Потоков до 90% пика | 16–32 тыс. |
| Round trip одного dispatch (commit + wait) | 156 мкс |
| Dispatch внутри одного command buffer | 0.6–0.8 мкс |

Следствия:

- Такт за тактом с CPU гонять нельзя: 156 мкс на dispatch против ~2.5 мкс на такт EH1 на P-ядре.
  Ядро должно крутить тысячи тактов внутри одного dispatch, а тестбенч — жить на GPU.
- Для насыщения GPU нужны десятки тысяч потоков, а память M4 вмещает около 10 тыс. экземпляров
  EH1 (1.23 МБ на экземпляр, `recommendedMaxWorkingSetSize` 12.7 ГБ). Значит, на M4 потолок по
  числу экземпляров задаёт память, а не вычисления.

## Как устроен прототип

```
RTL + тестбенч ──verilator --cc──▶ C++ модели ──vl2metal.py──▶ sim.metal + gpu_root.h
                                      │                              │
                                      ▼                              ▼
                          CPU: initial, $readmem,         GPU: eval-цикл, N экземпляров,
                          settle → снимок состояния ──▶   тысячи тактов на dispatch
```

1. **Тестбенч без файлового I/O** (`eh1/make_tb.py`): из пути каждого такта убраны `exec.log`,
   строки и ассоциативные массивы; результат теста пишется в переменную `gpu_status`.
2. **Verilator → MSL** (`vl2metal/vl2metal.py`). Транслятор текстовый: берёт сгенерированный
   Verilator C++ и переписывает обращения к состоянию.
   - Раскладка AoSoA: экземпляры группами по 32 (SIMD-группа), каждое скалярное поле — массив по
     32 лейнам: `vlSelfRef.x` → `vlSelfRef.x[L]`. Соседние потоки читают соседние адреса.
   - Большие массивы (ICCM, DCCM) — `[элемент][лейн]`: если экземпляры читают один адрес, доступ
     тоже объединяется.
   - В Metal попадают только функции, достижимые из eval-цикла; `$display` выбрасывается,
     `$finish` ставит флаг.
3. **Рантайм** (`vl2metal/verilated_metal.h`): MSL-порты нужных хелперов из `verilated_funcs.h`,
   бит в бит.
4. **Хост** (`vl2metal/host.mm`): инициализирует CPU-модель, копирует её состояние в N лейнов,
   крутит ядро, затем повторяет прогон на CPU и сравнивает **всё** состояние лейна с CPU-моделью.

### Компиляция: одно ядро не собирается

Если отдать Metal всю модель одной функцией (Verilator по умолчанию, всё инлайнится), бэкенд
компилятора (`MTLCompilerService`) не уложился и в 12 минут, съев 2.4 ГБ памяти; прогон я
остановил. Рабочий вариант:

- `verilator --output-split-cfuncs 1000` режет большие функции `_nba_*` на куски (123 функции
  вместо 29);
- `vl2metal.py --noinline` запрещает их инлайнить в ядро.

Пайплайн собирается за **2.6 с**. Цена: Verilator переносит часть временных переменных из
локальных в поля состояния: 9.1 КБ скалярного состояния на экземпляр вместо 8.1 КБ.

Сборка:

```bash
apple/gpu/eh1/build_cpu.sh cpu_split "--output-split-cfuncs 1000" -O2
apple/gpu/vl2metal/build.sh apple/gpu/work/eh1/cpu_split/obj_dir Vtb_top core_clk \
    tb_top__DOT__gpu_status apple/gpu/work/eh1/metal_split --noinline
cd apple/gpu/work/eh1/cpu_split   # program.hex для инициализации
../metal_split/host ../metal_split/sim.metallib 4096
```

## Сиды и случайные числа

Экземпляр с сидом N ведёт себя так же, как CPU-модель с `+verilator+seed+N`.

- **Генератор на экземпляр.** На CPU `$urandom` берёт числа из генератора потока
  (xoroshiro128\*\*, `VlRNG` в `include/verilated.cpp`). На GPU у каждого экземпляра своё
  состояние генератора: поля `__Vgpu_rng0/1`, 16 байт. `vl2metal.py` передаёт его во все вызовы
  `VL_RANDOM_*`/`VL_URANDOM_*`, а `verilated_metal.h` повторяет генератор бит в бит.
  Поддерживаются `$random`, `$urandom`, `$urandom_range`, широкие значения и пересев
  (`$random(seed)`, `$urandom(seed)`).
- **Инициализация.** Хост запускает initial-блоки на CPU с сидом экземпляра и переносит на GPU
  состояние модели и генератора. Если initial-блоки первого сида не взяли ни одного случайного
  числа, их состояние от сида не зависит. Тогда хост копирует его во все экземпляры, и
  экземпляры отличаются только генератором. Хост определяет это сам. Для EH1 это 0.2 с вместо
  40 мс на сид (`$readmemh` и предзагрузка памяти), то есть 163 с на 4096 сидов.
- **Проверка.** Хост повторяет на CPU несколько экземпляров (`--verify`) с их сидами и сравнивает
  всё состояние модели и состояние генератора.

Проверено на `rng/rng_tb.sv`: случайный трафик через FIFO с табло, на каждом такте
`$urandom`, `$urandom_range`, `$random` и 96-битное значение. В дизайн заложена ошибка, которая
срабатывает на редких случайных данных, поэтому часть сидов падает. На 512 сидах набор упавших
(119) одинаков в режимах `cpu`, `gpu` и `both`. Вариант `+define+RESEED` проверяет пересев и
initial-блок со случайными числами, когда инициализация идёт отдельно для каждого сида.

Не поддерживаются: `randomize()` и constraints (классы), генератор процесса (`std::process`),
plusargs модели на GPU.

## Регрессия на CPU и GPU из одной очереди (`apple/tools/batch_run.py`)

```bash
# EH1 со случайными задержками шины: модель для CPU (PGO) и для GPU
apple/gpu/eh1/build_cpu.sh cpu_stall "--output-split-cfuncs 1000" -O2 "--stall 20"
apple/gpu/vl2metal/build.sh apple/gpu/work/eh1/cpu_stall/obj_dir Vtb_top core_clk \
    tb_top__DOT__gpu_status apple/gpu/work/eh1/metal_stall --noinline
cd apple/gpu/work/eh1/cpu_stall
../../../../tools/pgo_build.py --obj-dir obj_dir -- ./obj_dir/Vtb_top +verilator+seed+1

# --on cpu | gpu | both
../../../../tools/batch_run.py --on both --runs 10000 --pass-regex TEST_PASSED \
    --link program.hex --gpu-host "../metal_stall/host ../metal_stall/sim.metallib" \
    -- ./obj_dir/Vtb_top +verilator+seed+{seed}
```

- `--on cpu`: только процессы на CPU (`-j`, по умолчанию все ядра).
- `--on gpu`: только GPU, CPU свободен для другой работы. Пакеты по `--gpu-batch` сидов
  (по умолчанию 4096, оптимум M4). CPU занят только запуском хоста, проверкой одного экземпляра
  на пакет (`--gpu-verify`) и перезапуском упавших сидов.
- `--on both`: CPU-процессы берут сиды из очереди по одному, GPU — пакетами.

На GPU нет `$display`, поэтому упавшие на GPU сиды перезапускаются на CPU: так появляется лог, а
заодно результат GPU подтверждается. Сид, который упал на GPU, но прошёл на CPU, выводится как
`MISMATCH`: это ошибка трансляции, а не дизайна. `--no-rerun` отключает перезапуск.

Как `both` делит работу. Пакет на GPU идёт столько же, сколько один прогон, умноженный на
замедление экземпляра на GPU. Для EH1 это около 400 с против 0.45 с на P-ядре. Поэтому маленький
остаток очереди CPU доделает быстрее, чем GPU. Планировщик даёт GPU полный пакет, пока не знает
время пакета. Дальше он даёт пакет, только если CPU не успеет разобрать остаток за это время, и
уменьшает пакет на то, что CPU разберёт параллельно.

## Результаты на M4 (VeeR EH1, CoreMark, 250 тыс. тактов)

Корректность: на полном прогоне все **4096 из 4096** экземпляров дошли до TEST_PASSED, и итоговое
состояние лейнов совпало с CPU-моделью бит в бит (проверены первый и последний).

### Сколько экземпляров запускать

Окно 8 тыс. тактов, одинаковые экземпляры:

| Экземпляров | Млн экземпляро-тактов/с | Память |
|---|---|---|
| 32 | 0.08 | 0.04 ГБ |
| 256 | 0.47 | 0.3 ГБ |
| 1024 | 1.22 | 1.3 ГБ |
| 2048 | 1.77 | 2.5 ГБ |
| 4096 | 2.46 | 5.0 ГБ |
| 6144 | 2.70 | 7.6 ГБ |
| 8192 | не помещается в один `MTLBuffer` (10 ГБ) | |

Размер threadgroup (32–256) не влияет. Полный прогон 4096 экземпляров: 410 с, **9.98 прогона
CoreMark в секунду**.

**Оптимум для M4: 4–6 тыс. экземпляров.** Ниже 4 тыс. GPU недогружен. Выше рост маленький, а память
на 16-гигабайтной машине кончается.

### Расхождение экземпляров

| Сценарий | Млн экземпляро-тактов/с |
|---|---|
| Все экземпляры одинаковые | 2.46 |
| Разные точки программы, фаза клока совпадает (`--stagger 2`, `38`) | 2.34–2.38 |
| Фазы клока внутри SIMD-группы различаются (`--stagger 1`, `37`) | 1.01–1.03 |

Расхождение по управлению почти бесплатно: код Verilator за такт в основном без ветвлений. Дорого
только, если в одной SIMD-группе часть лейнов на posedge, а часть на negedge: тогда GPU исполняет
оба пути. В регрессии одного дизайна клок у всех экземпляров общий, поэтому это не мешает. Для
дизайнов с независимыми клоками или `--timing` это ограничение.

### GPU против CPU

Эталон CPU — тот же тестбенч без логирования, PGO, `batch_run.py`.

| Конфигурация | Прогонов CoreMark/с | Млн экземпляро-тактов/с |
|---|---|---|
| CPU, 1 процесс | 2.2 | 0.55 |
| CPU, 10 процессов (все ядра) | 11.0 | 2.76 |
| GPU, 4096 экземпляров | 10.0 | 2.49 |
| **GPU 4096 + CPU 9 процессов одновременно** | **~20.9** | **~5.2** |

- На M4 GPU даёт столько же, сколько весь CPU, а не в разы больше.
- GPU и CPU почти не мешают друг другу (CPU 10.93 против 11.0 соло, GPU 2.48 против 2.49), поэтому
  вместе пропускная способность удваивается.
- Поправка к прошлым замерам: с `exec.log` CPU выдавал 3.86 прогона/с, без него — 11. Логирование
  тестбенча стоило почти втрое больше, чем всё, что даёт CPU-тюнинг.

### Что ограничивает GPU

Скорее всего, полоса памяти. Скалярное состояние EH1 — 9.1 КБ на экземпляр, вычислений два на
такт. Если каждое читает и пишет почти всё состояние, при 2.7 млн экземпляро-тактов/с это
~80–90 ГБ/с при пике копирования 99 ГБ/с. Счётчики GPU это не подтвердили: `xctrace` из командной
строки их не отдал, так что это оценка.

Что не помогло:

- Порог `--output-split-cfuncs` 3000 и 10000 вместо 1000: 2.36 и 2.28 млн против 2.38. Компиляция
  растёт до 15 с и 334 с.
- Размер threadgroup: не влияет.

### Энергия: та же регрессия только на CPU и только на GPU

Регрессия из 8192 сидов EH1 со случайными задержками шины (`--stall 20`): каждый сид — полный
CoreMark, 250 тыс. тактов, все прошли в обоих режимах. CPU — `batch_run.py --on cpu`, PGO,
10 процессов; GPU — `--on gpu`, два пакета по 4096. Мощность снималась `macmon` раз в секунду
(`apple/bench/energy.py`). Мощность всего Mac берётся с датчика системной мощности SMC
(`sys_power`): это вся машина по постоянному току, без потерь блока питания. Перед каждым
прогоном 2 минуты простоя для базовой линии.

| | Только CPU | Только GPU | CPU / GPU |
|---|---|---|---|
| Время регрессии | 707 с (11.6 прогона/с) | 868 с (9.4 прогона/с) | 0.81 |
| Средняя мощность Mac | 35.5 Вт | 12.5 Вт | 2.8 |
| в том числе CPU / GPU / RAM | 24.7 / 0 / 0.3 Вт | 0.15 / 4.8 / 2.2 Вт | |
| **Энергия Mac на регрессию** | **25.1 кДж (7.0 Вт·ч)** | **10.8 кДж (3.0 Вт·ч)** | **2.3** |
| Энергия Mac на один прогон | 3.06 Дж | 1.32 Дж | 2.3 |
| Сверх простоя (1.6–1.7 Вт) на регрессию | 23.9 кДж | 9.4 кДж | 2.5 |
| Вентилятор, макс. | 2955 об/мин | 1002 об/мин | |
| Температура CPU / GPU, макс. | 82 / 67 °C | 63 / 58 °C | |

- **GPU тратит на ту же регрессию в 2.3 раза меньше энергии** всего Mac, хотя идёт на 23% дольше.
  На CPU-регрессии P-ядра работают на 4.5 ГГц и вместе с E-ядрами потребляют 25 Вт. GPU работает
  на 1.58 ГГц и потребляет 4.8 Вт.
- Около 5–10 Вт мощности Mac не попадают ни в CPU, ни в GPU, ни в RAM: это шина SoC,
  контроллер памяти, SSD (CPU-режим пишет `run.log` на каждый прогон) и прочее. Поэтому
  отношение по всему Mac (2.3×) меньше, чем по одним вычислительным блокам.
- Ошибка измерения: мощность в установившемся режиме стабильна (CPU: 35.62 ± 0.13 Вт),
  интервал выборки 1 с на 700–870 с прогона, так что случайная ошибка меньше 1%. Систематическую
  ошибку датчика SMC я не проверял: внешнего ваттметра нет. На отношение CPU/GPU она влияет
  меньше, чем на абсолютные числа.
- Для сравнения `--on both` на тех же 8192 сидах: **434 с** (18.9 прогона/с, по 4096 сидов на CPU и
  на GPU), 39.6 Вт, 17.2 кДж, 2.10 Дж на прогон. Это быстрее всего, а по энергии посередине.
  Последние ~80 с CPU уже простаивал и ждал пакет GPU: пакет в 4096 сидов идёт около 430 с.
- Скорость GPU на варианте с `$urandom` в каждом такте и сидами — 9.4 прогона/с с учётом запуска
  хоста и проверки, против 9.98 без генератора: генератор и расхождение сидов стоят около 5%.

### Новые чипы: экстраполяция, не замер

Модель по замерам на M4:

- нужно около 450 экземпляров на ядро GPU, чтобы его загрузить;
- пропускная способность пропорциональна полосе памяти;
- потолок по числу экземпляров — память (1.23 МБ на экземпляр EH1).

| Чип | Ядер GPU | Полоса | Экземпляров для загрузки | Оценка GPU, млн экз.-тактов/с |
|---|---|---|---|---|
| M4 | 10 | 120 ГБ/с | 4–6 тыс. | 2.5–2.7 (замер) |
| M4 Pro | 16–20 | 273 ГБ/с | 8–9 тыс. | ~6 |
| M4 Max | 32–40 | 410–546 ГБ/с | 15–18 тыс. | ~9–12 |

Для этих чипов цифры — оценка. Перед покупкой железа под эту задачу её надо проверить: на старших
чипах может упереться в другое (кэши, выборка инструкций). У CPU M4 Pro и M4 Max тоже больше
P-ядер, поэтому соотношение GPU/CPU растёт медленнее полосы: примерно до 1.5–2× на M4 Max.

## Ограничения прототипа

- Транслятор текстовый, поддерживает подмножество: один клок, `--threads 1`, без DPI, `--timing`,
  классов, строк и ассоциативных массивов в коде такта. `$display` выбрасывается.
- Тестбенч приходится адаптировать: убрать файловый вывод, записывать результат в переменную.
- Случайные числа: см. «Сиды и случайные числа»; `randomize()` не поддерживается.

## Как довести до инструмента

Генератор на экземпляр и планировщик «CPU + GPU» уже сделаны (см. выше). Осталось:

1. Бэкенд в Verilator (`V3EmitC`), а не текстовый транслятор: он знает типы, клоки и границы
   функций и может сразу генерировать раскладку AoSoA. Ориентир по объёму — RTLflow.
2. Буфер вывода на экземпляр вместо `$display`: кольцевой буфер в общей памяти, который CPU
   форматирует после прогона. Пока вместо этого упавшие сиды перезапускаются на CPU.
3. Plusargs и `randomize()` на GPU.
