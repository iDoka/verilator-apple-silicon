# Verilator на Apple Silicon: как запускать быстрее

Рекомендации по замерам на Mac mini M4 (4P + 6E), дизайн VeeR EH1 с CoreMark. Цифры и методика —
в `BENCHMARKS.md`, разбор гипотез — в `RESEARCH.md`.

## Какой режим выбрать

| Задача | Рецепт | Выигрыш на M4 |
|---|---|---|
| Одна длинная симуляция (отладка, загрузка ОС, бенчмарк) | `--threads` = P-ядра − 1, `-O2`, компиляторный PGO | **1.83×** к `--threads 1 -Os` |
| Много прогонов одной модели (регрессия, сиды, набор тестов) | `--threads 1`, `-O2`, PGO, все ядра заняты отдельными процессами | **2.6×** по пропускной способности к лучшему одиночному прогону |

Многопоточная модель на регрессии проигрывает: потоки модели синхронизируются на каждом такте, а
независимые процессы — нет. Поэтому для регрессии каждый процесс однопоточный, а параллелизм — между
прогонами.

## Рецепт 1: одна длинная симуляция

```bash
P=$(sysctl -n hw.perflevel0.logicalcpu)        # число P-ядер, 4 на M4
verilator --cc --exe --threads $((P - 1)) [флаги] top.sv tb.cpp
apple/tools/pgo_build.py --obj-dir obj_dir -- ./obj_dir/Vtop [аргументы типичного прогона]
```

`pgo_build.py` собирает модель с `-O2 -fprofile-generate`, запускает обучающий прогон, сливает профиль
(`xcrun llvm-profdata`) и пересобирает с `-fprofile-use`. Обучающий прогон — типичный тест этой
модели. Горячий код — логика дизайна, поэтому профиль одного теста обычно подходит и для других тестов
той же модели; на EH1 это не проверялось. После изменения RTL профиль надо снять заново: устаревший
профиль не ломает сборку, но выигрыш пропадает.

Почему так:

- **Потоков не больше, чем P-ядер.** Статическое расписание ждёт самый медленный поток на каждом шаге,
  поэтому один поток на E-ядре тормозит всю модель: на M4 `--threads 6` медленнее, чем `--threads 1`.
  Verilator в этой ветке предупреждает об этом при запуске.
- **P − 1, а не P.** Одно P-ядро остаётся системе и тестбенчу: 3 потока на M4 стабильно быстрее 4.
- **`-O2` вместо `-Os` по умолчанию** даёт +5%, а вместе с PGO `-O2` лучше и `-Os`, и `-O3`.
- **PGO** даёт +17–26%: компилятор раскладывает горячие ветки подряд, и front-end меньше простаивает.
- На чипах Pro и Max P-ядер больше, и они разбиты на несколько кластеров. Обмен между кластерами
  дороже, поэтому P − 1 потоков там не обязательно лучший вариант: подбирайте число потоков на своём
  дизайне. На таком железе это не проверялось.

## Рецепт 2: регрессия из многих прогонов

```bash
verilator --cc --exe --threads 1 [флаги] top.sv tb.cpp
apple/tools/pgo_build.py --obj-dir obj_dir -- ./obj_dir/Vtop [аргументы типичного теста]
apple/tools/batch_run.py --runs 1000 --pass-regex TEST_PASSED --link program.hex \
    -- ./obj_dir/Vtop +verilator+seed+{seed}
```

`batch_run.py` держит занятыми все ядра (по умолчанию `-j` = все ядра, P + E). Каждый прогон
работает в своём каталоге: тестбенч может писать логи в текущий каталог. Каталоги прошедших прогонов
удаляются, у упавших остаётся `run.log`, в конце печатается список упавших сидов.

Замер на M4 (60 прогонов):

| Параллельных прогонов | Прогонов в секунду |
|---|---|
| 1 | 0.95 |
| 4 (только P-ядра) | 3.3 |
| 10 (все ядра) | 3.7–3.9 |
| для сравнения: по одному на `--threads 3` + PGO | 1.46 |

Шесть E-ядер вместе добавляют к четырём P-ядрам только около 15%. Если параллельно идёт другая
работа, `-j` по числу P-ядер теряет немного.

## Ловушки

- **Фоновые задачи launchd в 6 раз медленнее.** Процесс с `ProcessType=Background` (или запущенный
  через `taskpolicy -b`) macOS держит только на E-ядрах на минимальной частоте, и изнутри программы
  это не обойти. Запускайте регрессию из терминала, из CI-агента с обычным приоритетом или из
  launchd-задачи с `ProcessType=Interactive`.
- **`--autoflush`** замедляет EH1 в 1.5 раза: каждая строка лога сбрасывается на диск. Оставляйте его
  только для отладки падений.
- **`-mcpu=apple-m4`, ThinLTO, Thread PGO** (`--prof-pgo`) на EH1 ничего не дали.
- **Кэш-линия.** На E-ядрах гранула когерентности 128 Б, а Verilator выравнивает данные потоков по
  64 Б. Пока потоков не больше, чем P-ядер, это не мешает.
