# Verilator на Apple Silicon M4: ресёрч и гипотезы

Дата: 2026-11-14. Замеры — в `BENCHMARKS.md`.

## Итоги проверки

| Гипотеза | Результат |
|---|---|
| H1: кэш-линия 128 Б | **Частично.** Гранула когерентности: P-кластер — 64 Б, E-кластер — 128 Б (микробенч, false sharing до 3.3×). На VeeR EH1 эффекта не видно, потому что E-ядра медленные сами по себе. Фикс дешёвый, но неприоритетный. |
| H2: P/E-ядра | **Подтверждена, крупно.** `--threads 6` на M4 медленнее одного потока (0.92× против 1.78× при 3 потоках). QoS-патч не помогает. Рецепт: `--threads` не больше числа P-ядер минус 1. |
| H3: флаги, PGO | **Подтверждена.** `-O2`/`-O3` против `-Os`: +5–8%. Компиляторный PGO: +17–26%. `-mcpu=apple-m4`, LTO, Thread PGO: 0. |
| H4: `thread_local` | **Снята.** +0.4 нс на доступ. |
| Батч: N процессов | Пропускная способность в **2.6 раза** выше лучшего одиночного прогона. E-ядра добавляют около 15%. |
| H5–H9 | Не мерились. |

## Машина

Mac mini M4: 4 P-ядра и 6 E-ядер, 16 ГБ, macOS 26.3. Подробности — `../silero-tts-apple/docs/HW.md`.

| Ресурс | P-ядро | E-ядро |
|---|---|---|
| L1i | 192 КБ | 128 КБ |
| L1d | 128 КБ | 64 КБ |
| L2 (на кластер) | 16 МБ | 4 МБ |
| `hw.cachelinesize` | 128 Б | 128 Б |

SME2 есть, SVL 512 бит. SVE вне streaming mode нет (SIGILL).

## Какой это workload

По публикациям, код, который генерирует Verilator, — скалярный, ветвистый, целочисленный, с огромным
статическим кодом. Узкое место — **front-end** процессора: промахи L1i и iTLB, ошибки предсказания
переходов.

- RTeAAL Sim (arXiv 2601.18140): у Verilator 80–120 промахов L1i на 1000 инструкций (MPKI). Доля
  ошибок предсказания на RocketChip-4c: 22% на Xeon и 0.22% на Graviton 4.
- ARMOR (arXiv 2608.08462): более 50% столлов конвейера приходится на front-end.
- Документация Verilator: «the instruction cache often limits large models».

Отсюда два следствия для M4:

1. У M4 L1i 192 КБ (у x86 — 32 КБ), страницы 16 КБ (iTLB покрывает в 4 раза больше кода), широкий
   декодер. Поэтому M4 **уже хорош** для Verilator «из коробки», а x86-ориентированные настройки
   (`-Os` по умолчанию) могут быть здесь неоптимальны.
2. Векторные ускорители (NEON, SME2, GPU, ANE) напрямую ускоряют только то, чего в этом коде мало:
   регулярные вычисления над данными.

## Гипотезы, по ожидаемому выигрышу

### H1. False sharing: выравнивание под 64 Б при линии 128 Б (только `--threads` > 1)

**Факт из кода.** `include/verilatedos.h:503`: `#define VL_CACHE_LINE_BYTES 64`. На этом макросе
построена вся защита от false sharing:

- `VlThreadProgress` (`verilated_threads.h:61`) — счётчик прогресса каждого потока. При `alignas(64)`
  счётчики двух потоков попадают в одну 128-байтную линию. Тогда `publish()` одного потока выбивает
  линию у всех, кто ждёт *другой* поток.
- `V3VariableOrder`: переменные группируются по набору MTask-писателей, и каждая группа выравнивается
  по `VL_CACHE_LINE_BYTES`. Комментарий в файле прямо говорит: «Separating writers is enough to avoid
  false sharing». На M4 это неверно: две группы с разными писателями делят 128-байтную линию.
- `alignas(VL_CACHE_LINE_BYTES)` у Syms и у класса модели.

**Внешние подтверждения.** Go (`x/sys/cpu`) и crossbeam (`CachePadded`) используют 128 Б для
arm64/darwin. Есть оговорка: по сообщениям с Asahi Linux, `CTR_EL0` показывает 64 Б для L1, а 128 Б —
это гранула L2 и когерентности. Для false sharing решает именно гранула когерентности.

**Проверка.** Микробенч `apple/micro/false_sharing.cpp`: кольцо из N потоков с release/acquire, как в
`VlThreadProgress`, шаг 64 против 128 Б. Затем VeeR и SweRV с `--threads 2..4` и
`VL_CACHE_LINE_BYTES` 64 против 128.

**Фикс.** `VL_CACHE_LINE_BYTES 128` для `__APPLE__ && __aarch64__`. Возможно, для всего aarch64:
Neoverse V-серии тоже 64 Б, решать по данным. Изменение небольшое, upstream-friendly.

### H2. Гетерогенные ядра: E-ядра в статическом расписании

Статическое расписание MTask (`V3ExecGraph`) и Thread PGO предполагают одинаковые ядра. На macOS нет
thread affinity: `numaAssign` работает только на Linux. Поток может попасть на E-ядро, которое
в 2–3 раза медленнее, и тогда весь критический путь ждёт его в `waitFor()`.

- При `--threads` > 4 на M4 часть потоков **гарантированно** работает на E-ядрах.
- Worker-потоки создаются без явного QoS и наследуют его от main. Если процесс запущен с пониженным
  QoS (из IDE или через launchd), потоки могут оказаться на E-ядрах и при `--threads` ≤ 4.

**Проверка.** `--threads 1..8`; запуск с `taskpolicy -c utility` против дефолта. Потоки в
`verilator_gantt` (`--prof-exec`).

**Фикс (кандидат).** Worker-потоки на macOS создавать с `QOS_CLASS_USER_INTERACTIVE`
(`pthread_attr_set_qos_class_np`). Документировать, что на Apple разумный максимум `--threads` — число
P-ядер (`hw.perflevel0.physicalcpu`). Возможно, рантайм должен предупреждать, если потоков больше
числа P-ядер.

### H3. Флаги компиляции модели: `-Os` по умолчанию, PGO, LTO, порядок функций

`OPT_FAST = -Os` выбран для экономии L1i на x86 (32 КБ). У M4 L1i в 6 раз больше, поэтому `-O2`,
`-O3` и `-mcpu=apple-m4` могут выиграть.

Компиляторный PGO (`-fprofile-instr-generate` / `-fprofile-instr-use`) делает раскладку кода
hot/cold и правильные веса веток. Для front-end-bound кода это обычно даёт 10–30%. Плюс
`-Wl,-order_file` (поддерживается ld64 / ld-prime) и LTO.

**Проверка.** Матрица `OPT_FAST` × {нет PGO, PGO} на VeeR EH1/EH2/EL2 CoreMark.

**Фикс.** Документация или рецепт в `verilated.mk` для Apple. Изменения кода минимальны.

### H4. `thread_local` на Mach-O — это вызов функции

На Linux доступ к TLS в исполняемом файле — модель initial-exec, одна инструкция `mrs tpidr_el0`
плюс смещение. На Darwin каждый доступ идёт через TLV-дескриптор и вызов thunk'а `tlv_get_addr`.
Проверено: `clang -S` для `t_s.mtaskId = id` даёт пролог кадра и `blr`.

Сгенерированный код на **каждый MTask** делает `Verilated::mtaskId(id)`, `mtaskId(0)` и проверку
`t_endOfEvalReqd` в `endOfThreadMTask` (`V3ExecGraph.cpp:1146-1150`). Это примерно три TLV-вызова
на MTask. Те же вызовы — в `vl_invokeExecGraph`, а также в `$display` и `$time` через
`threadContextp()`.

**Проверка.** Микробенч `apple/micro/tls_cost.cpp`, затем профиль MT-модели: доля `tlv_get_addr`.

**Фикс (кандидат).** Ожидаемый выигрыш небольшой (единицы нс на MTask). Имеет смысл, только если
профиль покажет заметную долю.

### H5. Аллокатор: libmalloc против mimalloc

Это касается тестбенчей с классами, очередями, строками, корутинами `--timing` и UVM. Аллокатор macOS
медленнее glibc и mimalloc на мелких объектах.

**Проверка.** `DYLD_INSERT_LIBRARIES` с mimalloc на UVM-тестах и на `t_cores_*_cmark` с `--timing`.

**Фикс.** Только документация: линковать с mimalloc.

### H6. NEON — точечно

- Широкие сигналы хранятся как `VlWide<N>` из **32-битных** слов (`VL_EDATASIZE 32`). На 64-битной
  платформе вдвое больше операций, чем нужно. Перейти на 64-битные слова — огромная переделка
  (V3Expand, emit, рантайм), не стоит этого без профиля.
- Runtime-функции `VL_*_W` (циклы по словам) clang частично автовекторизует. Проверить в профиле.
- Трассировка (`chg*Data`) — сравнения разбросаны по памяти, это gather. NEON почти не поможет.

### H7. SME2 — нет

SME-блок на M4 **один на кластер**, а не на ядро. Вход и выход `smstart`/`smstop` стоят около 7 нс:
по данным Jena, при 8 FMOPA на блок пропускная способность 434 GFLOPS против пиковых 2008. SSVE без
матричных инструкций на M4 медленный. Логика RTL — скалярная и ветвистая. Единственная теоретическая
ниша — bit-parallel симуляция сотен стимулов (512-битные предикаты), но это другой продукт.

### H8. GPU (Metal) — только для batch-стимулов или гейт-уровня

- **RTLflow** (ICPP'22): транспиляция C++ Verilator в CUDA, один экземпляр дизайна на поток GPU.
  40× против 80 CPU-потоков на 65 536 стимулах (NVDLA). Полезно для регрессии с тысячами сидов,
  бесполезно для одной симуляции.
- **GEM** (DAC'25): синтез в AIG, виртуальная VLIW-машина на GPU, до 64× на одном стимуле. Есть форк
  **Jacquard** с Metal-бэкендом. Это не Verilator: нужен гейт-уровень и синтез.
- Для одной RTL-симуляции через Verilator латентность dispatch в Metal (десятки мкс) больше, чем
  время целого `eval()` (единицы мкс). Unified memory убирает копирование, но не латентность.

#### Разбор RTLflow и перенос на M4

**Как работает RTLflow.**

- Транспайлер работает поверх AST Verilator. Каждая переменная становится массивом в формате SoA
  `varN[N*offset + tid]`, по 4 пула `uint8/16/32/64`. Один GPU-поток соответствует одному стимулу,
  поэтому доступы coalesced.
- Граф RTL режется на задачи, каждая задача — CUDA-ядро. Разбиение подбирается MCMC-поиском с
  реальными прогонами и даёт 3–6%.
- Задачи исполняются как CUDA Graph: 2.6–7.6× против streams.
- Конвейер «CPU готовит входы группы i+1, пока GPU считает группу i» даёт до +79%.
- Цикломатическая сложность кода снижается с 16 до 5: ветвления заменяются вычислениями.

**Цифры из статьи** (A6000 против 80 потоков Xeon 6138):

| Число стимулов | Результат |
|---|---|
| ≤256 | GPU проигрывает (NVDLA: 0.4–0.9×) |
| 1024 | паритет или небольшой выигрыш |
| 16K–65K | 16–47× |

**Перенос на M4.** У GPU M4 около 1280 ALU-лейнов (у A6000 — 10 752) и 120 ГБ/с общей с CPU памяти
(у A6000 — 768 ГБ/с). То есть примерно 1/8 по вычислениям и 1/6 по полосе. Зато CPU M4 значительно
слабее 80-поточного Xeon по агрегату, поэтому отношение GPU/CPU для M4 сжимается не в 8 раз, а
примерно в 2–3.

**Состояние VeeR EH1** (измерено, `sizeof(Vtb_top___024root)`):

| Часть | Размер |
|---|---|
| Всё состояние | 1.23 МБ |
| Скалярные сигналы | 7.4 КБ |
| `VlWide` | 0.9 КБ |
| Массивы (ICCM, DCCM, регфайлы) | 1.21 МБ |
| `__text` бинарника | 0.89 МБ |

**Потолок GPU по полосе.** На каждый такт за экземпляр через DRAM проходит около 8 КБ сигналов
туда-обратно. При 120 ГБ/с это порядка 10 млн экземпляро-тактов в секунду на весь GPU.

**Сколько экземпляров влезет.** Память ICCM и DCCM на экземпляр — 1.2 МБ. В 16 ГБ, которые делятся
с CPU, помещается порядка 8 тыс. экземпляров.

**Вывод (исправлен после замеров).** Изначально я предполагал, что CPU M4 даёт около 9 млн
экземпляро-тактов в секунду, и получал паритет с GPU. Замер показал **0.97 млн** на всём CPU
(очередь из 10 процессов, `BENCHMARKS.md`). Один такт VeeR EH1 стоит P-ядру около 4 мкс, это порядка
десятков тысяч инструкций.

Потолки GPU M4 (оценка):

| Ограничение | Оценка, экземпляро-тактов в секунду |
|---|---|
| Полоса памяти: 120 ГБ/с при 16–24 КБ трафика на экземпляро-такт | 5–7.5 млн |
| Вычисления: 1280 лейнов × 1.4 ГГц, около 50 тыс. операций на такт | около 36 млн без дивергенции |

То есть теоретически это **в 2–7 раз больше всего CPU M4** для пакета из тысяч стимулов. Это
порядок, а не измерение. Дивергенция, uncoalesced-доступ к массивам и ёмкость памяти (около 8 тыс.
экземпляров) съедят часть выигрыша. До инвестиций в транспайлер нужна roofline-проба на Metal.

**Плюсы Apple.**

- Unified memory: узкое место RTLflow `set_inputs` (CPU→GPU) исчезает, входы пишутся прямо в общий
  буфер.
- Самодостаточный тестбенч (программа в ICCM, как здесь CoreMark) позволяет крутить тысячи тактов
  внутри одного dispatch, без CPU на каждом такте.
- MSL — подмножество C++14, близко к тому, что генерирует Verilator.

**Минусы Apple.**

- Нет аналога CUDA Graph, есть Indirect Command Buffers.
- Watchdog на долгие command buffers.
- Нельзя DPI, UVM, `--timing`, `$display` в горячем пути.

#### CPU-альтернатива той же идее: батч по стимулам на CPU

1. **N процессов по 1 потоку вместо `--threads`.** Масштабируется почти линейно. Страницы кода
   общие между процессами, значит, общий L2. Это базовая линия для любого batch-ускорения, мерить
   первой.
2. **Lane-batching на NEON.** Тот же SoA-транспайл, что в RTLflow, но лейн — NEON-вектор: 4×32
   или 16×8 бит. Один поток инструкций обслуживает 4–16 стимулов. Это бьёт ровно в главное узкое
   место — front-end и L1i: стоимость выборки и декодирования делится на число лейнов. Ветвления
   превращаются в select, как в RTLflow. Генератор можно сделать общим с Metal, потому что
   `ext_vector_type` в clang и векторные типы MSL похожи.

### H9. ANE — нет

ANE — fp16-MAC-движок с dispatch через CoreML (порядка мс). Битовых и целочисленных операций нет.
Прикладной смысл для RTL-симуляции отсутствует.
